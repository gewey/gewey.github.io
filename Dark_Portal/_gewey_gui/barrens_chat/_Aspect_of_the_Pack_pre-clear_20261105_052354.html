**You were right about the browser, and right about the architecture.** Corrected one detail:

A page opened over `file://` **cannot** fetch a sibling `.md`. It has an opaque origin, so `fetch()`/XHR gets blocked by CORS. But a `<script>` tag is **exempt** from that rule. So the JS *can* read the chat files — just not as markdown. It has to read something already shaped for JS.

That's the split I built:

| | Python | JS |
| --- | --- | --- |
| Role | **writer** | **reader** |
| Reads | `.md` files | `__Pack_Data.js` |
| Writes | `__Pack_Data.js` + renders the page | swaps DOM text in place |
| Needs to run | yes, for data to change | free — it's just the page |

So: **`__Furious_Howl.py` publishes `__Pack_Data.js`**, and `../_js/__Furious_Howl.js` polls it with a cache-buster and swaps the three `<pre>` blocks in place. **No reload, no flicker, scroll position preserved.** Joey's window just sits there and updates.

**The one thing that still needs Python:** the data has to be regenerated, which is a filesystem write. A browser cannot touch disk. That's not a limitation I can engineer around — it's the sandbox. Hence `--watch`:

```powershell
python __Furious_Howl.py --watch
```

Polls the three `.md` files once a second, regenerates on change. Verified: I appended a line, it detected and updated `html+data` within one tick. Leave it running in a terminal and the page is genuinely live.
