Seven Silences, And Why They Matter

7 of the twelve names return nothing at all: tandieu, tandaria, tantalous, tankadu, gehenna, theorycrafters, ebbesson.

The guild is not on this disk

gehenna - 0 hits in 0 files. theorycrafters - 0 hits in 0 files. That is not a bug in the sweep: the retail install has no guild cache, no guild roster dump, no guild chat log. Every guild line that exists for me lives outside the client, in Wipefest report pages and in the raid-log archive.

This is the tenure rule's best friend. A machine that holds no guild text cannot tempt me into re-adopting a 2009-2016 capture of a guild I was not in. The disk is silent, so the only guild claim that can be made is the one the 2019 logs make.

Not the same as gone. <Theorycrafters> still stands on Hyjal-US: Raider.IO answers it 200, Horde, 76 members, last crawled 2026-03-15 - and the roster carries none of the Tandu handles. Thrall-US answers 400 (no such guild). The guild outlived the tenure; the tenure is the part worth protecting.

The surname is a folder, not a string

ebbesson - 0 hits. The surname in Tandumonium-Ebbeson survives in exactly one place on this install: the directory Hyjal\Jacobebbeson\. No file inside the client spells it. The name was carried by a character slot, not by config.

Same for tandieu - the 2008 spelling has no line anywhere in the retail tree. It survives in the web record and in the persona wing, nowhere else.

Read this page's zeros as evidence of absence, not proof the name never existed. Case-folded whole-word matching over 319 text files cannot see inside .dmp crash dumps, compiled .blob/.toc pairs, or the 38 vendor addon folders this pass skipped.

What The Own-Code Failures Were

Tandumonium_UI.lua:26

attempt to call a nil value - session 1, 2026-08-18 03:04 UTC. The first boot of the addon on this client. Line 26 sits in the top-level chunk, so something the file expected to exist at load time (a shared table, or a helper another addon was supposed to have registered) was not there yet.

Tandumonium_UI.lua:435

attempt to call a nil value inside BuildOptionsPanel, session 19, same evening. The stack shows TandumoniumUIOptionsPanel already built with its title and hint fontstrings assigned - the frame existed, one call inside it did not.

WowheadQuickLink.lua:15 and the double binding

Session 25, 2026-08-26 09:04 UTC. My module failed at line 15 and the client warned that WOWHEAD_QUICK_LINK_NAME and WOWHEAD_QUICK_LINK_RAIDERIO_NAME were loaded more than once, sourced from the vendor addon's Bindings.xml. Two implementations of one idea were live: the CurseForge addon and mine. Only one could own the key, and the client kept both.

Tandumonium_UI_UMPD.lua:69

attempt to compare nil with number, one minute later. The pin engine compared a saved distance that had never been written, so the comparison met nil. A one-line default would have saved the session.

Bindings.xml rejected outright

Sessions 26 and 27: Unrecognized XML attribute: category, then Unrecognized XML: Binding with attribute: name and attribute: header. The client's XML reader refused my binding schema outright - not a Lua error, a parser rejection. This is the exact failure the Kintsugi doctrine exists for: never edit the vendor addon, patch around it at runtime.

Then the tape goes quiet

The last own-code line is 2026-08-26 09:38. After that the only two entries are a stray DeM frame error and a BugSack permissions warning on 2026-09-04. Whatever was fixed in those nine days held: the install has not blamed my code since.

The Macro Tape

Logs\AccountData.log.old is the client's macro and account-data dump. It holds 3518 macro records between 8/18 06:47:17.209 and 8/26 13:00:54.941, and one of them repeats 35 times. Not a bug: the dump is written at many points inside a session - every logout, every reload - so the repetition is the calendar.

VER 3 000000000000014F "@World" "136017"
/btwl a Tandu
/run SetTracking(10, true)
/run SetTracking(10, false)
END

What the macro does

@World is a hunter utility macro, not a combat button. /btwl a Tandu is BtWLoadouts' alias command - it applies the loadout stored under the name Tandu. Then it flips tracking on and off in the same press through two /run lines, which is the cheapest way to refresh a tracking type the client will not re-apply while it is already active.

The loadout is named after the short handle, not the long one. Even in a file that has 329 reasons to write Tandumonium, the thing my hands typed is Tandu.

What else is on the tape

/acp disableall - 105 lines. /reload ui (bound to mouse button 2) - 105 lines. A session of addon-by-addon bisection: disable everything, reload, re-enable one at a time, and watch the error tape on the previous section fill up.

That is how the Bindings.xml rejection in session 27 got found, and it is why the vendor-fracture list on Tandu Legacy is specific instead of vague.

Method & Limits

Two read-only scanners, both local, both gitignored, nothing written inside the game tree:

Research/_local/_retail_echo.py    ->  _raw/retail_echo.json
Research/_local/_echoes_build.py   ->  _gewey_gui/Echoes.html

The census is case-folded whole-word matching over 319 text files (4,461,432 bytes). tandu is matched with word boundaries so Tandulari is not double-counted as tandu + lari; tandumonium is matched as a substring because it is one word in every file that holds it.

What this cannot see: text inside .dmp crash dumps (binary), inside compiled addon .blob files, inside the 38 vendor addon folders, inside Cache\ CDN archives, or anywhere the client stored a name encoded rather than spelled. A zero here means 'no plain-text line', not 'never happened'.
The external sweep is unchanged this pass and stays walled: Warcraft Logs answers 403, WowProgress 403, the Wayback CDX API 429, Brave 429, DuckDuckGo 202. Bing answers 200 with markup, but quoted rare-token queries return unrelated results for these names, so nothing from it was recorded. Current state of every door: Web Ledger.
